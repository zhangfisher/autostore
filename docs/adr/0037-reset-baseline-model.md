# reset 采用基线快照模型，而非操作逆放

`reset` 原按路径记录 `oldValue` 并在恢复时逐条写回。根因是**数组族操作的前像在 Operate 契约里没有承载位**：`insert`/`remove` 的 `oldValue` 恒为 `undefined`、`path` 挂在数组自身，`delete` 的旧值则落在 `value` 字段。结果是 push/pop/splice 后 `reset` 把整个数组写成 `undefined`，`delete` 的键恢复成 `undefined` 而非消失，`list.length = n` 更是让 `setVal` 抛异常且状态半写不回滚。改为：路径首次变脏时捕获**基线**，恢复的对象是基线而非被逆放的操作序列。

## 关键取舍

**为何不补 Operate 契约而改用基线**：为数组族操作补前像要动整个数组族契约，波及 syncer、devtools 与广播派生逻辑。基线模型把复杂度关在 reset 内部。

**为何对象存旧引用、数组存元素表**：对象的脏只来自整体替换（改子属性记在子路径上），旧引用仍完整；数组是原地改的，引用已失效，必须拷贝元素表。数组基线在 `hookArray` 内 `method.apply` **之前** slice 捕获——不动 reactive 的公开契约。

**为何折叠为节点级写回**：恢复一个容器本质上是把旧引用还回去，逐下标写回既慢又要单独处理 `length` 收缩。计算属性靠广播派生自通知，syncer/devtools 是快照式的，react/form/viewer 均为精确路径订阅——折叠对它们全部安全。

**为何计算属性路径不排除 operate 标记**：用 `computedObjects.has(pathKey)` 判定（key 即 `path.join(".")`，`observers.ts` 保证注册早于首次回写），不给 Operate 加新字段。此举顺带修掉"仅读取计算属性即变脏"——初始化写回与每次重算写回都不再入表。

**为何拒绝容量上限**：一旦有上限，"哪些变更被静默丢弃"就成为新的语义难题，而 reset 是调试/测试特性，砍掉可预测性不划算。

**为何单下标赋值也拍全表**：只记下标会导致"先 `arr[0]=9`、后 `push`"时全表基线捕获已被改动的数组、旧值被剪掉而丢失还原。要避免须引入基线合成规则（下标位移使"子记录属于哪个下标"不再直观），易错且会让"基线"从无例外的概念退化为需要推理的概念。O(n) 内存/脏容器换取绝对正确是划算的。

**为何基线采集只读原始快照**：捕获基线一律取自 operate 的 `oldValue`、`hookArray` 的 `method.apply` 前像或原始对象，**禁止经由 Proxy 读取状态**。Proxy 的 `get` 陷阱会在**正在求值的计算属性**中注册依赖、污染依赖追踪，并触发访问事件。因此同步捕获是安全的——它对状态树完全只读。

## 重置范围（`resetable: boolean | string[]`）

`resetable` 从布尔扩展为路径规则集合。判定为**首匹配即止**：规则按书写顺序依次匹配，命中即决定该路径是否可重置，不再检查后续规则。

```ts
resetable: ['!orders.items', 'orders']
//   orders.items     → 命中规则 1 → 不可重置，止
//   orders.price     → 规则 1 不命中 → 规则 2 命中 → 可重置
```

顺序因此是有意义的：**更靠前的规则遮蔽更靠后的规则**。`['orders','!orders.items']` 里规则 2 是死代码——`orders` 整棵子树都先被规则 1 命中，规则 2 永不被检查。

零命中时的兜底由有无纳入规则决定：存在纳入规则 → 默认不可重置（故 `['orders.items']` = 只有它）；只有排除规则 → 默认可重置（故 `['!x']` = 除 x 外都记）。兜底只在零命中时生效，此时不存在"首匹配"可言，因此与首匹配优先不冲突。

**为何首匹配即止**：两阶段判定（先扫完纳入规则、再扫完排除规则）要求每条路径跑完整个规则表。首匹配即止让命中路径提前退出——规则表越长、命中越靠前，节省越大。

**为何不用"未匹配即记"的纯黑名单**：那样正向规则永久无效（未匹配也记、匹配也记），`['orders.items']` 会静默退化为"记全部"，而用户按纳入规则理解——无声的期望错配比报错危险得多。

**规则模式中 `**` 含根**：与"前缀含根"（`orders` 覆盖 `orders` 整棵子树）保持一致，否则 `!orders.items` 排除 `orders.items` 自身而 `!orders.**` 不排除 `orders` 自身，规则语义自相矛盾。**不改 `isPathMatched`**——它服务 watch 路径，`**` 不含自身是 ADR-0003 的刻意设计；规则另写匹配函数。（附注：`**` 含根后，`orders.**` 与 `orders` 等价，`**` 的独立用途只剩显式表达"全记"与 `!**` 表达"全不记"。）

**为何空数组是特例**：`resetable: []` 与 `false` 完全等价——不安装监听器、零开销、清空记录。它是"禁用"而非"空规则集"，故与 `['!x']`（安装监听器、除 x 外都记）语义不同。

## 容器基线与排除规则的共存

"被判为不可重置的路径绝不会被恢复"与"容器整体写回"直接冲突：`['!orders.items','orders']` 下 `orders.items` 被规则 1 判为不可重置，而 `orders` 命中规则 2 → 拍容器基线 = 旧引用 → 整体写回会把 `orders.items` 一并还原。

解决：**恢复期用同一个匹配函数复算**。整体写回某节点前先探测"是否存在以本节点为前缀的更长规则"，有则改为逐 `own key` 写回并逐后代复算判定——递归深度由不可重置路径的深度决定，与子树大小无关。子树内无此情况时整体写回，折叠完整保留。

顺序相关的情形会自动退化：`['orders','!orders.items']` 中无任何路径被判为不可重置（规则 2 是死代码），于是不触发递归、整体写回完整保留。

对比另一方案"记录期拒绝拍容器基线、降级为逐叶子记录"：后者内存 O(未排除叶子数) 最差、事件数等于叶子数。过滤恢复内存 O(脏容器数) 最省、事件数等于该容器 `own key` 数。代价是"排除子 + 纳入父"这类混合配置下，那一层从 1 条事件变为 `own key` 条事件。

## 对象引用与数组元素表的覆盖能力不同

"容器基线吸收其后代"对二者并不对称，实现必须区别对待：

- **对象旧引用**在写入那一刻即脱离状态树，此后不再被改动，故它**完整覆盖**其后代——捕获容器基线后，其后代的变更不再单独记录。
- **数组元素表**与活数组**共享元素对象**，元素被原地改写会同时改到快照里。故数组基线**不覆盖**后代：元素（含更深层）的变更仍单独记录，还原时按"祖先先于后代"的顺序先还数组、再还后代。

由此推出两条实现规则：

1. 捕获容器基线前检查子树内是否已有脏路径——有则**不捕获**。旧引用已经带上后代的变更，整体捕获会吞掉那些后代的还原；此时降级为保留后代基线，还原退化为逐个脏路径。
2. 数组基线的后代必须能被单独记录，故判断"是否已被祖先覆盖"时只看**对象型**祖先。

## 后果

- `reset` 的承诺由"逆放操作"变为"回到基线"，语义需在文档中写明——它与"撤销"的直觉不同，不写清楚会被当 bug 报回来。
- **禁止用 `setTimeout`/`queueMicrotask` 推迟记录**：`reset()` 与变更是同 tick 的同步调用（`resetable.test.ts` 甚至直接断言 `updatedState`），宏/微任务必然排在 `reset()` 之后 → 记录为空、`reset` 退化为 no-op；且推迟后读到的是变更后的值，已非基线。若担心基线采集干扰正常更新流程，解法是"只读原始快照"（见上），不是延迟。
- 规则**顺序有意义**，文档必须给出 `['!a','a']` 与 `['a','!a']` 的对照例子，否则用户无从判断哪条规则是死代码。
- 恢复永不抛异常：预检路径可写性，逐条 try/catch，失败项收集后 warn，仅清成功项。
- `reset(entry)` 未命中静默无操作（正常 API 调用，"该子树无可恢复变更"不是错误）；store 整体未启用时仍 warn。
- **已知且接受**：`onAny` 类订阅者（watchAll）只收祖先事件、不收广播派生事件，故 `@autostorejs/plugins/watch` 与 `@autostorejs/plugins/shadow` 在 reset 期间不会刷新。修复它们需改动 core 的事件架构（推翻 ADR-0001），本次范围外。
- `updatedState` 降级为只读调试视图，不再是恢复依据。
- **子树内已有脏路径后再整体替换父容器**，该容器不捕获基线，还原降级为逐个脏路径——父容器新引入的其它字段不会被清除。这是"不静默给出错误结果"的取舍。
- 采集期每次数组变更都要判断"子树内是否已有脏路径"（扫描基线表），最坏 O(基线条目数)。reset 是调试/测试特性，可接受。
- `resetable` 的采集回调装在 reactive 的 options 上（而非 Proxy 陷阱内联），`false` / `[]` 时完全不挂载，禁用态零开销。
- 规则判定落在每次写操作上：`resetable: true`（无规则）走零匹配开销的快路径，`false`/`[]` 不安装监听器——两条主路径的运行时开销与改造前持平；只有配置了规则的 store 承担匹配成本。
